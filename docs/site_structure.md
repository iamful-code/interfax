# Что известно о структуре e-disclosure.ru (и что не проверено)

Живого доступа к сайту при разработке не было (сетевая политика окружения; кроме того, сайт отдаёт
**403 при запросах не с российских IP** — по опыту открытых проектов). Ниже — сводка из открытых
источников и предположения, которые нужно подтвердить командой `disclosure-alpha discover`.

## Предположения (проверить через discover)
* Имена полей формы поиска: `dateStart`, `dateFinish`, `lastPageNumber`, `lastPageSize`,
  `eventTypeCheckboxGroup` (чекбоксы типов), `query`/`queryId`, `eventTypeTerm`, `radView`.
  Переопределяются в `config/edisclosure_form.json` → `{"field_map": {"date_from": "...", ...}}`.
* Форма отправляется POST на тот же адрес; результаты — таблица со строками «дата | компания | сообщение».
  Парсер не зависит от вёрстки: берёт ближайший `tr`/`li`/`div` вокруг ссылки на событие.
* Максимальный размер страницы — вероятно 100 (`lastPageSize`); если сайт игнорирует номер страницы,
  клиент останавливается по повтору идентификаторов.
* Список типов сообщений (идентификаторы чекбоксов) — извлекается из формы (`event_type_options()`),
  затем сопоставляется с категориями `config/event_types.yaml` по регулярным выражениям.
* Поиск компании по ИНН — страница `poisk-po-kompaniyam` (структура не проверена); запасной путь —
  поиск по сообщениям с `query=<ИНН>` и чтение `company.aspx?id=` из результатов.

## Что делает `discover`
Скачивает страницу поиска, ленту, одно событие и одну компанию; сохраняет HTML в `data/discovery/`,
а в `discovery.json` — найденные формы (все поля, чекбоксы с подписями), ссылки `/portal/...` и
URL-подобные строки из скриптов (ajax-эндпоинты). По этому файлу за пару минут подтверждаются или
правятся имена полей — без изменения кода.

## Что выяснилось при первой проверке доступа (сентябрь 2026)
* Перед сайтом стоит защита с JS-проверкой браузера: первый запрос получает страницу-заглушку
  (спиннер, блок под капчу, редирект для клиентов без JavaScript), скрипт которой выставляет cookies
  `spjs`, `spsc`, `spid` и перезагружает настоящую страницу. Код ответа при этом 200, поэтому
  распознавать заглушку нужно по содержимому (`is_protection_stub`).
* Без браузерных заголовков запросы получают HTTP 503 с `Retry-After: 60`.
* Сервер -- Angie (форк nginx); приложение -- ASP.NET Core MVC (cookies `.AspNetCore.Antiforgery.*`,
  `.AspNetCore.Mvc.CookieTempDataProvider`, заголовок `app-version`). Значит форма поиска защищена
  antiforgery-токеном: скрытое поле `__RequestVerificationToken` нужно брать со страницы формы и
  отправлять вместе с POST (клиент делает это и обновляет токен при отказе 400/403).
* Ответы отдаются в UTF-8; заголовки запрещают кеширование (`no-store, no-cache`).
* Старые адреса `/portal/event.aspx?EventId=`, `/portal/company.aspx?id=`, `/portal/lastnews.aspx`
  отвечают, но проверить их разметку до прохождения защиты не удалось.
* Обход: режим `--browser` (Playwright + Chromium). Браузер открывает страницу поиска, проходит проверку,
  после чего все запросы идут через сетевой контекст браузера (`APIRequestContext`) -- те же cookies и
  TLS-отпечаток. Если ответ снова оказывается заглушкой, выполняется повторный прогрев.
  Проверено на локальном стенде, повторяющем механику проверки (`tests/test_browser.py`).
* Помимо JS-проверки защита может показать капчу с поворотом картинки (скрипты `sp_rotated_captcha/…`).
  Она распознаётся отдельно (`classify_page` -> `captcha`): в видимом окне команда ждёт, пока её пройдёт
  человек, в скрытом -- сразу сообщает, что нужен `--show-browser`. Пройденная капча живёт в профиле браузера.

## Устройство нового сайта (подтверждено на живых данных, сентябрь 2026)
| Что | Как |
|---|---|
| Страница поиска | `/poisk-po-soobshheniyam`, форма `#sEventSearchForm`, кнопка «Искать» `#sendButton`, результаты вставляются в `#searchResults` |
| Поля формы | `dateStart`, `dateFinish` (ДД.ММ.ГГГГ), `lastPageNumber`, `lastPageSize`, `eventTypeCheckboxGroup` (повторяется), `districtsCheckboxGroup`, `regionsCheckboxGroup`, `branchesCheckboxGroup`, `textfieldCompany` (ИНН/ОГРН/ОКПО), `textfieldEvent`, `query`, `queryEvent`, `radView`, `radReg`, `__RequestVerificationToken` |
| Поиск (то же, что делает страница) | `POST /api/search/sevents`, тело -- форма (`application/x-www-form-urlencoded`), обязательны заголовок `RequestVerificationToken` и `X-Requested-With: XMLHttpRequest`; без них ответ `{"errors":["E001"]}`. **Ответ -- JSON**: `{"foundEventsList":[{"companyID":..,"companyName":..,"eventName":..,"pseudoGUID":..,"agency":..,"highlighted":..}], "totalCount":N}`; идентификатор сообщения (`pseudoGUID`) подставляется в `/portal/event.aspx?EventId=...` |
| Справочник типов сообщений | `GET /api/data/sevent-types` -> `[{"id":136,"name":"..."}]`, около 300 типов |
| Вход в личный кабинет | `POST /api/account/login` (нам не нужен) |
| Адреса сообщений и компаний | прежние: `/portal/event.aspx?EventId=...&q=`, `/portal/company.aspx?id=...` |
| Размер страницы | по умолчанию 10; `lastPageSize=100` работает |

Значения фильтров «все» кодируются как `-1` (округа, регионы, отрасли), `radReg=FederalDistricts`, `radView=0`.

## Сколько данных есть (проверено 25.09.2026)
Фильтр по типам работает: идентификаторы берутся из справочника сайта и передаются повторяющимся
полем `eventTypeCheckboxGroup`. Но сообщений категории «изменение доли участия члена органа управления»
за 2026 год найдено **одно** (АО «Радуга», 16.06.2026, раскрыто через ИА АК&М).

Причина, скорее всего, в послаблениях раскрытия с 2022 года: эмитентам разрешили ограничивать
публикацию чувствительных сведений, и этот тип сообщений практически исчез. Значит гипотезу о сделках
инсайдеров нужно проверять на архиве 2012-2021 годов, а не на свежих данных. Команда
`disclosure-alpha counts --categories insider_stake_change --from 2012 --till 2026` показывает
распределение по годам (число берётся из поля `totalCount`, без обхода страниц).
